## 企画

![cs-planning](../../img/agents/cs-planning.png)

Deep Agent は、単一のコンテキスト ウィンドウ内でアドホックに推論するのではなく、更新、再試行、回復が可能な構造化されたタスク プランを維持します。これは、エージェントを長期的な目標に向かって導く生きた ToDo リストと考えてください。これを体験するには、Claude Code または Codex を計画用に試してみてください。タスクを実行する前に有効にすると、結果が大幅に向上します。

私たちは最近、Claude Code を使用した長時間にわたるブレインストーミングの力についても書きました。これは、計画、専門家のコンテキスト、および人間参加型の力を示しています (専門知識は、ディープ エージェントと連携するときに重要な優位性をもたらします)。計画は長期的な問題にも重要です (次に来る科学的発見のためのエージェントを考えてください)。

## オーケストレーターとサブエージェントのアーキテクチャ

![cs-subagents](../../img/agents/cs-subagents.png)

1 つの大きなエージェント (通常は非常に長いコンテキストを持つ) ではもはや十分ではありません。見たことがある[引数](https://cognition.ai/blog/dont-build-multi-agents)マルチエージェント システムには反対し、モノリシック システムには賛成ですが、私はこれについては懐疑的です。

The orchestrator-sub-agent architecture is one of the most powerful LLM-based agentic architectures you can leverage today for any domain you can imagine.オーケストレーターは、検索エージェント、コーダー、KB レトリーバー、アナリスト、検証者、ライターなどの特殊なサブエージェントを管理し、それぞれが独自のクリーン コンテキストとドメイン フォーカスを持ちます。

オーケストレーターはインテリジェントに委任し、サブエージェントは効率的に実行されます。オーケストレーターは、その出力を統合して一貫した結果を生成します。 Claude Code は、コーディングとサブエージェントに対するこのアプローチの使用を普及させました。これは、(関心の分離を通じて) コンテキストを効率的に管理するのに特に有用であることがわかりました。

オーケストレーターとサブエージェントの使用の力についていくつかのメモを書きました[ここ](https://x.com/omarsar0/status/1960877597191245974)そして[ここ](https://x.com/omarsar0/status/1971975884077965783).

## コンテキストの取得とエージェント検索

![persistent-storage](../../img/agents/cs-persistent-storage.png)

Deep Agent は会話履歴だけに依存しません。ファイル、メモ、ベクトル、データベースなどの外部メモリに中間作業を保存し、モデルのコンテキストをオーバーロードすることなく重要なものを参照できるようにします。高品質の構造化記憶は美しいものです。

などの最近の作品を見てみましょう[推理銀行](https://arxiv.org/abs/2509.25140)そして[エージェントコンテキストエンジニアリング](https://arxiv.org/abs/2510.04618)メモリの構築と回復をより最適化する方法に関するいくつかの本当に素晴らしいアイデアをご覧ください。オーケストレーターとサブエージェントのアーキテクチャで構築するということは、ハイブリッド メモリ技術 (エージェント検索 + セマンティック検索など) も活用でき、使用する戦略をエージェントに決定させることができることを意味します。

## コンテキストエンジニアリング

このような種類のエージェントとやり取りするときにやってしまう最悪のことの 1 つは、指定が不十分な指示やプロンプトを行うことです。迅速なエンジニアリングはこれまでも重要でしたが、私たちは新しい用語を使用します。[コンテキストエンジニアリング](https://www.promptingguide.ai/guides/context-engineering-guide)エージェントのコンテキストを構築することの重要性を強調します。指示は、いつ計画するか、いつサブエージェントを使用するか、ファイルに名前を付ける方法、および人間と共同作業する方法を定義するために、より明確かつ詳細で意図的なものである必要があります。コンテキスト エンジニアリングの一部には、構造化された出力、システム プロンプトの最適化、コンテキストの圧縮、コンテキストの有効性の評価、および[ツール定義の最適化](https://www.anthropic.com/engineering/writing-tools-for-agents).

詳細については、コンテキスト エンジニアリングに関する以前のガイドをお読みください。[コンテキストエンジニアリングの詳細](https://www.promptingguide.ai/guides/context-engineering-guide)

## 検証

![verification agent](../../img/agents/cs-verification-agent.png)

コンテキスト エンジニアリングに次いで、検証はエージェント システムの最も重要なコンポーネントの 1 つです (ただし、あまり議論されません)。検証は、要約すると出力を検証することですが、これは自動化 (LLM-as-a-Judge) することも、人間が行うこともできます。最新の LLM は (数学やコーディングなどの分野で) テキストを生成するのに効果的であるため、依然として幻覚、お調子者、プロンプト インジェクション、およびその他の多くの問題に悩まされていることは忘れられがちです。検証は、エージェントの信頼性を高め、本番環境に対応できるようにするのに役立ちます。体系的な評価パイプラインを活用することで、優れた検証ツールを構築できます。
