# LLM の検索拡張生成 (RAG)

import { Callout } from 'nextra/components'

LLM を扱う場合、ドメイン知識のギャップ、事実の問題、幻覚など、多くの課題があります。 Retrieval Augmented Generation (RAG) は、データベースなどの外部知識を使用して LLM を強化することで、これらの問題の一部を軽減するソリューションを提供します。 RAG は、継続的に更新される知識を必要とする知識集約的なシナリオやドメイン固有のアプリケーションで特に役立ちます。他のアプローチに対する RAG の主な利点は、LLM をタスク固有のアプリケーション用に再トレーニングする必要がないことです。 RAG は、会話型エージェントへの応用により最近普及しました。

この概要では、「[大規模言語モデルの検索拡張生成: 調査](https://arxiv.org/abs/2312.10997) (Gao et al., 2023). In particular, we focus on the existing approaches, state-of-the-art RAG, evaluation, applications and technologies surrounding the different components that make up a RAG system (retrieval, generation, and augmentation techniques).

## Introduction to RAG

!["RAG Framework"](../../img/rag/rag-framework.png)

もっとよく紹介されたように[ここ](https://www.promptingguide.ai/techniques/rag)、RAG は次のように定義できます。

> RAG は入力を受け取り、ソース (Wikipedia など) が指定された一連の関連/サポート文書を取得します。ドキュメントは元の入力プロンプトとコンテキストとして連結され、最終出力を生成するテキスト ジェネレーターに供給されます。これにより、RAG は時間の経過とともに事実が変化する可能性がある状況に適応できるようになります。 LLM のパラメトリック知識は静的であるため、これは非常に役立ちます。 RAG を使用すると、言語モデルが再トレーニングをバイパスできるようになり、検索ベースの生成を通じて信頼性の高い出力を生成するための最新情報にアクセスできるようになります。

つまり、RAG で取得された証拠は、LLM の応答の精度、制御性、および関連性を強化する方法として機能します。これが、高度に進化する環境で問題に対処する際に、RAG が幻覚やパフォーマンスの問題を軽減するのに役立つ理由です。

RAG には事前トレーニング方法の最適化も含まれていますが、現在のアプローチは、RAG の長所と次のような強力な微調整モデルを組み合わせることに大きく移行しています。[ChatGPT](https://www.promptingguide.ai/models/chatgpt)そして[Mixtral](https://www.promptingguide.ai/models/mixtral)。以下のグラフは、RAG 関連研究の進化を示しています。

さまざまなステップ/コンポーネントを次のように説明します。

- **入力：**&#x4C;LM システムが応答する質問は、入力と呼ばれます。 RAG が使用されない場合は、質問に応答するために LLM が直接使用されます。
- **インデックス作成:**&#x52;AG を使用する場合、一連の関連ドキュメントは、最初にそれらをチャンク化し、チャンクの埋め込みを生成し、ベクトル ストアにインデックス付けすることによってインデックス付けされます。推論時にも同様の方法でクエリが埋め込まれます。
- **検索：**&#x95A2;連ドキュメントは、クエリをインデックス付きベクトルと比較することによって取得され、「関連ドキュメント」とも呼ばれます。
- **世代：**&#x95A2;連するドキュメントは、追加のコンテキストとして元のプロンプトと結合されます。結合されたテキストとプロンプトは、応答生成のためにモデルに渡され、その後、ユーザーへのシステムの最終出力として準備されます。

示されている例では、モデルを直接使用すると、現在の出来事に関する知識が不足しているため、質問に応答できません。一方、RAG を使用すると、システムはモデルが質問に適切に答えるために必要な関連情報を取得できます。

## RAG Paradigms

過去数年にわたって、RAG システムは Naive RAG から Advanced RAG、Modular RAG へと進化してきました。この進化は、パフォーマンス、コスト、効率に関する特定の制限に対処するために発生しました。

!["RAG Framework"](../../img/rag/rag-paradigms.png)
*[図のソース](https://arxiv.org/abs/2312.10997)*

### Naive RAG

Naive RAG は、前述した従来のインデックス作成、取得、生成のプロセスに従います。つまり、ユーザー入力を使用して関連ドキュメントをクエリし、プロンプトと組み合わせてモデルに渡し、最終応答を生成します。アプリケーションに複数ターンの対話対話が含まれる場合、会話履歴をプロンプトに統合できます。

Naive RAG には、低精度 (取得されたチャンクの位置がずれている) や低い再現率 (関連するチャンクをすべて取得できない) などの制限があります。また、LLM に古い情報が渡される可能性もあります。これは、RAG システムが最初に解決を目指すべき主要な問題の 1 つです。これは、幻覚の問題や不十分で不正確な応答につながります。

拡張を適用すると、冗長性と繰り返しの問題が発生する可能性もあります。取得した複数の文章を使用する場合は、順位付けとスタイル/トーンの調和も重要です。もう 1 つの課題は、生成タスクが拡張情報に過度に依存しないようにすることです。これにより、モデルが取得したコンテンツを繰り返すだけになる可能性があります。

### Advanced RAG

Advanced RAG は、取得前、取得、取得後のプロセスの最適化を含む取得品質の向上など、Naive RAG に存在する問題に対処するのに役立ちます。

事前取得プロセスには、データのインデックス作成の最適化が含まれます。これは、データ粒度の強化、インデックス構造の最適化、メタデータの追加、位置合わせの最適化、および混合検索の 5 つの段階を通じて、インデックス付けされるデータの品質を向上させることを目的としています。

コンテキストを構成するチャンクの品質に直接影響を与える埋め込みモデル自体を最適化することで、取得段階をさらに改善できます。これは、エンベディングを微調整して検索の関連性を最適化するか、コンテキストの理解をより適切に捕捉する動的エンベディング (OpenAI の embeddings-ada-02 モデルなど) を採用することで実現できます。

取得後の最適化は、コンテキスト ウィンドウの制限を回避し、ノイズの多い情報や気が散る可能性のある情報に対処することに重点を置いています。これらの問題に対処する一般的なアプローチは再ランキングです。これには、関連するコンテキストをプロンプトの端に再配置したり、クエリと関連するテキスト チャンクの間の意味論的な類似性を再計算したりするアプローチが含まれる場合があります。即時圧縮も、これらの問題に対処するのに役立つ場合があります。

### Modular RAG

Modular RAG は、その名前が示すように、類似性検索のための検索モジュールの組み込みや取得側での微調整の適用など、機能モジュールを強化します。 Naive RAG と Advanced RAG はどちらも Modular RAG の特殊なケースであり、固定モジュールで構成されています。拡張 RAG モジュールには、さまざまな問題を解決する検索、メモリ、フュージョン、ルーティング、予測、およびタスク アダプターが含まれます。これらのモジュールは、特定の問題の状況に合わせて再配置できます。したがって、Modular RAG は、タスク要件に基づいてモジュールを追加または交換したり、モジュール間のフローを調整したりできるため、多様性と柔軟性が向上します。

RAG システムの構築における柔軟性の向上を考慮して、RAG パイプラインを最適化するために次のような他の重要な最適化手法が提案されています。

- **ハイブリッド検索の探索:**&#x3053;のアプローチでは、キーワードベースの検索やセマンティック検索などの検索手法を組み合わせて、関連性のあるコンテキスト豊富な情報を取得します。これは、さまざまなクエリ タイプや情報ニーズに対処する場合に役立ちます。
- **再帰的検索およびクエリ エンジン:**&#x518D;帰的な取得プロセスが含まれます。このプロセスは、小さな意味論的なチャンクから開始し、その後、コンテキストを強化するより大きなチャンクを取得する可能性があります。これは、効率とコンテキスト豊富な情報のバランスをとるのに役立ちます。
- **ステップバックプロンプト:** [促すテクニック](https://arxiv.org/abs/2310.06117)これにより、LLM は推論を導く概念と原則を生成する抽象化を実行できるようになります。これにより、LLM は特定のインスタンスから離れ、必要に応じてより広範な推論が可能になるため、RAG フレームワークに採用された場合に、より根拠のある応答が得られます。
- **サブクエリ:**&#x30C4;リー クエリやチャンクの順次クエリなど、さまざまなシナリオに使用できるさまざまなクエリ戦略があります。 LlamaIndex が提供するのは、[サブ質問クエリエンジン](https://docs.llamaindex.ai/en/latest/understanding/putting_it_all_together/agents.html#)これにより、クエリをさまざまな関連データ ソースを使用するいくつかの質問に分割できます。
- **仮説的なドキュメントの埋め込み:** [ハイデ](https://arxiv.org/abs/2212.10496)クエリを直接使用するのではなく、クエリに対する仮説的な回答を生成し、それを埋め込み、それを使用して仮説的な回答に類似したドキュメントを取得します。

## RAG Framework

このセクションでは、取得、生成、拡張など、RAG​​ システムのコンポーネントの主要な開発について要約します。

### 検索

取得は、取得者から関連性の高いコンテキストを取得する処理を行う RAG のコンポーネントです。レトリバーは、次のようなさまざまな方法で強化できます。

**意味表現の強化**

このプロセスには、レトリーバーを強化するセマンティック表現を直接改善することが含まれます。以下にいくつかの考慮事項を示します。

- **チャンク化:**&#x91CD;要なステップの 1 つは、扱うコンテンツと応答を​​生成するアプリケーションに応じて、適切なチャンク化戦略を選択することです。モデルが異なれば、ブロック サイズが異なると強度も異なります。文トランスフォーマーは単一の文ではパフォーマンスが向上しますが、text-embedding-ada-002 は 256 または 512 トークンを含むブロックでパフォーマンスが向上します。考慮すべきその他の側面には、ユーザーの質問の長さ、アプリケーション、トークンの制限などがありますが、RAG システムでの取得を最適化するために、さまざまなチャンク化戦略を実験するのが一般的です。
- **微調整された埋め込みモデル:**&#x52B9;果的なチャンク化戦略を決定したら、特殊なドメインを使用している場合は、埋め込みモデルを微調整することが必要になる場合があります。そうしないと、アプリケーション内でユーザーのクエリが完全に誤解される可能性があります。広範なドメイン知識 (つまり、ドメイン知識の微調整) と特定の下流タスクを微調整できます。[BGE-large-EN が BAAI を開発](https://github.com/FlagOpen/FlagEmbedding)は、検索の関連性を最適化するために微調整できる注目すべき埋め込みモデルです。

**クエリとドキュメントの調整**

このプロセスは、ユーザーのクエリを意味空間内のドキュメントのクエリと一致させる処理を行います。これは、ユーザーのクエリに意味情報が不足している場合、または不正確な表現が含まれている場合に必要になることがあります。以下にいくつかのアプローチを示します。

- **クエリのリライト:**&#x6B21;のようなさまざまな手法を使用してクエリを書き直すことに重点を置いています。[クエリ2ドキュメント](https://arxiv.org/abs/2303.07678), [ITER-RETGEN](https://arxiv.org/abs/2305.15294)、HyDE。
- **埋め込み変換:**&#x30AF;エリ埋め込みの表現を最適化し、タスクとより密接に連携した潜在空間に配置します。

**Aligning Retriever and LLM**

このプロセスでは、取得者の出力を LLM の設定に合わせて調整します。

- **レトリバーの微調整:**&#x4C;LM のフィードバック信号を使用して、検索モデルを改良します。例としては、増強に適応したレトリバー ([AAR](https://arxiv.org/abs/2305.17331)), [REPLUG](https://arxiv.org/abs/2301.12652)、 そして[UPRISE](https://arxiv.org/abs/2303.08518)、いくつか例を挙げると。
- **アダプター:**&#x8ABF;整プロセスを支援する外部アダプターを組み込みます。例としては次のものが挙げられます。[PRCA](https://aclanthology.org/2023.emnlp-main.326/), [RECOMP](https://arxiv.org/abs/2310.04408)、 そして[PKG](https://arxiv.org/abs/2305.04757).

### 世代

RAG システムのジェネレーターは、取得した情報を、モデルの最終出力を形成する一貫したテキストに変換する役割を果たします。このプロセスには多様な入力データが含まれるため、クエリやドキュメントから得られた入力データに対する言語モデルの適応を調整する作業が必要になる場合があります。これは、取得後のプロセスと微調整を使用して対処できます。

- **Frozen LLM による取得後:**&#x53D6;得後の処理では、LLM はそのままにし、代わりに情報圧縮や結果の再ランキングなどの操作を通じて取得結果の品質を向上させることに重点を置きます。情報圧縮は、ノイズの削減、LLM のコンテキスト長制限への対処、生成効果の強化に役立ちます。再ランキングの目的は、ドキュメントを並べ替えて、最も関連性の高い項目を最上位に優先させることです。
- **RAG 用の LLM の微調整:**&#x52;AG システムを改善するために、ジェネレータをさらに最適化または微調整して、生成されたテキストが自然であり、取得したドキュメントを効果的に活用できるようにすることができます。

### 増強

拡張には、取得したパッセージからのコンテキストを現在の生成タスクと効果的に統合するプロセスが含まれます。拡張プロセス、拡張ステージ、拡張データについて詳しく説明する前に、RAG のコア コンポーネントの分類を次に示します。

!["RAG Taxonomy"](../../img/rag/rag-taxonomy.png)
*[図のソース](https://arxiv.org/abs/2312.10997)*

検索拡張は、事前トレーニング、微調整、推論などのさまざまな段階で適用できます。

- **強化段階:** [RETRO](https://arxiv.org/abs/2112.04426)これは、検索拡張を利用して大規模な事前トレーニングをゼロから行うシステムの例です。外部の知識に基づいて構築された追加のエンコーダーを使用します。微調整を RAG と組み合わせて、RAG システムの有効性の開発と向上を支援することもできます。推論段階では、特定のタスクの要求を満たし、RAG プロセスをさらに洗練するために、取得したコンテンツを効果的に組み込むために多くのテクニックが適用されます。

- **拡張ソース:**&#x52;AG モデルの有効性は、拡張データ ソースの選択によって大きく影響されます。データは、非構造化データ、構造化データ、LLM 生成データに分類できます。

- **拡張プロセス:**&#x591A;くの問題 (マルチステップ推論など) では、1 回の検索だけでは十分ではないため、いくつかの方法が提案されています。
  - **反復検索**モデルが複数の検索サイクルを実行して、情報の深さと関連性を強化できるようになります。この方法を活用した注目すべきアプローチには次のものがあります。[RETRO](https://arxiv.org/abs/2112.04426)そして[GAR-meets-RAG](https://arxiv.org/abs/2310.20158).
  - **再帰的検索**1 つの取得ステップの出力を別の取得ステップへの入力として再帰的に繰り返します。これにより、複雑で複数のステップからなるクエリ (学術研究や訴訟分析など) に関連する情報をより深く掘り下げることができます。この方法を活用した注目すべきアプローチには次のものがあります。[IRCoT](https://arxiv.org/abs/2212.10509)そして[説明のツリー](https://arxiv.org/abs/2310.14696).
  - **適応型検索**取得に最適な瞬間とコンテンツを決定することで、特定の要求に合わせて取得プロセスを調整します。  この方法を活用した注目すべきアプローチには次のものがあります。[FLARE](https://arxiv.org/abs/2305.06983)そして[Self-RAG](https://arxiv.org/abs/2310.11511).

### RAG vs. Fine-tuning

RAG と微調整の違い、およびそれぞれがどのシナリオに適しているかについては、多くのオープンな議論があります。これら 2 つの分野の研究によると、RAG は新しい知識を統合するのに役立ち、微調整を使用すると、内部知識、出力形式を改善し、複雑な命令に従うことを教えることでモデルのパフォーマンスと効率を向上させることができます。これらのアプローチは相互に排他的ではなく、急速に進化する知識と、特定の形式、トーン、スタイルに従うカスタマイズされた応答へのアクセスを必要とする、複雑な知識集約型でスケーラブルなアプリケーションでの LLM の使用を改善することを目的とした反復プロセスで相互に補完できます。さらに、プロンプト エンジニアリングは、モデル固有の機能を活用することで結果を最適化するのにも役立ちます。以下の図は、他のモデル最適化手法と比較した RAG の異なる特性を示しています。

## RAG Evaluation

さまざまな側面で LLM のパフォーマンスを測定するのと同様に、評価は、さまざまなアプリケーション シナリオにわたる RAG モデルのパフォーマンスを理解し、最適化する上で重要な役割を果たします。従来、RAG システムは、F1 や EM などのタスク固有のメトリクスを使用して、下流タスクのパフォーマンスに基づいて評価されてきました。[ラレ](https://arxiv.org/abs/2308.10633v2)は、知識集約型タスク向けに検索拡張された大規模言語モデルを評価するために使用されるフレームワークの注目すべき例です。

RAG 評価ターゲットは、取得と生成の両方について決定されます。目標は、取得されたコンテキストの品質と生成されたコンテンツの品質の両方を評価することです。検索品質を評価するには、推奨システムや情報検索などの他の知識集約型ドメインで使用される NDCG やヒット率などの指標が使用されます。生成の品質を評価するには、ラベルのないコンテンツの場合は関連性と有害性、ラベル付きコンテンツの場合は正確さなど、さまざまな側面を評価できます。全体として、RAG 評価には手動または自動の評価方法が含まれます。

RAG フレームワークの評価では、3 つの主要な品質スコアと 4 つの能力に焦点を当てます。品質スコアには、コンテキストの関連性 (つまり、取得されたコンテキストの精度と特異性)、回答の忠実度 (つまり、取得されたコンテキストに対する回答の忠実度)、および回答の関連性 (つまり、提示された質問に対する回答の関連性) の測定が含まれます。さらに、RAG システムの適応性と効率の測定に役立つ 4 つの機能 (ノイズ耐性、否定的拒否、情報統合、反事実耐性) があります。以下は、RAG システムのさまざまな側面を評価するために使用されるメトリックの概要です。

いくつかのベンチマークのようなもの[RGB](https://arxiv.org/abs/2309.01431)そして[RECALL](https://arxiv.org/abs/2311.08147)RAG モデルを評価するために使用されます。のような多くのツール[RAGAS](https://arxiv.org/abs/2309.15217), [ARES](https://arxiv.org/abs/2311.09476)、 そして[トゥルーレンズ](https://www.trulens.org/trulens_eval/core_concepts_rag_triad/)RAG システムの評価プロセスを自動化するために開発されました。一部のシステムは、上で定義した品質スコアの一部を決定するために LLM に依存しています。

## RAGの課題と将来

この概要では、RAG 研究のいくつかの研究側面と、RAG システムの検索、拡張、生成を強化するためのさまざまなアプローチについて説明しました。以下にいくつかの課題を強調します。[Gao et al., 2023](https://arxiv.org/abs/2312.10997)RAG システムの開発と改善を続けると、次のようになります。

- **コンテキストの長さ:**&#x4C;LM はコンテキスト ウィンドウ サイズを拡張し続けており、関連性の高い重要なコンテキストを確実にキャプチャするために RAG をどのように適応させる必要があるかという課題が生じています。
- **堅牢性:**&#x52;AG での測定と改善には、反事実や敵対的な情報に対処することが重要です。
- **ハイブリッドアプローチ:**&#x52;AG モデルと微調整モデルの両方の使用を最適化する方法をより深く理解するための研究が継続的に行われています。
- **Expanding LLM roles:**&#x52;AG システムをさらに強化するために LLM の役割と機能を強化することには、高い関心が寄せられています。
- **スケーリングの法則:**&#x4C;LM スケーリングの法則の調査と、それが RAG システムにどのように適用されるかについては、まだ適切に理解されていません。
- **Production-ready RAG:**&#x5B9F;稼働グレードの RAG システムには、パフォーマンス、効率、データ セキュリティ、プライバシーなどにわたる卓越したエンジニアリングが求められます。
- **Multimodal RAG:**&#x52;AG システムに関しては多くの研究活動が行われてきましたが、そのほとんどはテキストベースのタスクに集中していました。画像、オーディオとビデオ、コードなど、より多くの領域で問題への取り組みをサポートするために、RAG システムのモダリティを拡張することへの関心が高まっています。
- **評価：**&#x52;AG を使用して複雑なアプリケーションを構築するには、文脈上の関連性、創造性、コンテンツの多様性、事実性などのさまざまな側面をより確実に評価できる微妙なメトリクスと評価ツールを開発するための特別な注意が必要です。さらに、RAG 用のより優れた解釈可能性の研究とツールも必要です。

## RAG Tools

RAG システムを構築するための一般的な包括的なツールには、次のものがあります。[LangChain](https://www.langchain.com/), [LlamaIndex](https://www.llamaindex.ai/)、 そして[DSPy](https://github.com/stanfordnlp/dspy)。次のようなさまざまな目的に応じたさまざまな専用ツールもあります。[Flowise AI](https://flowiseai.com/)RAG アプリケーションを構築するためのローコード ソリューションを提供します。その他の注目すべきテクノロジーとしては、[干し草の山](https://haystack.deepset.ai/), [メルターノ](https://meltano.com/), [コヒアコーラル](https://cohere.com/coral)、その他。ソフトウェアおよびクラウド サービス プロバイダーには、RAG 中心のサービスも含まれています。たとえば、Weaviate の Verba はパーソナル アシスタント アプリケーションの構築に役立ち、Amazon の Kendra はインテリジェントなエンタープライズ検索サービスを提供します。

## 結論

結論として、RAG システムは、カスタマイズを可能にし、幅広いドメインにわたる RAG のパフォーマンスと実用性をさらに高める、より高度なパラダイムの開発を含め、急速に進化しました。 RAG アプリケーションには大きな需要があり、RAG システムのさまざまなコンポーネントを改善する方法の開発が加速しています。ハイブリッド手法から自己検索まで、これらは最新の RAG モデルで現在検討されている研究分野の一部です。より優れた評価ツールと指標に対する需要も高まっています。以下の図は、RAG エコシステム、RAG を強化するためのテクニック、課題、およびこの概要で取り上げられているその他の関連する側面の概要を示しています。
